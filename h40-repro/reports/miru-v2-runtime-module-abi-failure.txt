ABI interpretation
------------------
The rebuilt kernel exports module_layout CRC:

  0xa9c6dadd

module_layout is the MODVERSIONS fingerprint generated from struct module,
struct modversion_info, struct kernel_param, struct kernel_symbol, and
struct tracepoint. The stock vendor modules contain a different expected CRC.
Matching uname/vermagic is therefore insufficient: the published-source build
does not currently implement the binary module ABI accepted by the shipped H.40
kernel.

CONFIG_MODULE_SIG_FORCE does not participate in the relevant module structure
definitions; disabling it exposed this mismatch but did not create it.

Oppo sibling-source check
-------------------------
The immediately relevant files in oppo-source/android_kernel_oppo_sm8150 at
66cbe4bd056bf032063026ce24a7159449c00f6e were compared with this branch:

  include/linux/module.h
  include/linux/moduleparam.h
  include/linux/export.h
  include/linux/tracepoint.h

They are byte-identical. The generic module-related sm8150-perf_defconfig
settings also match; the visible differences are principally OPPO/OPLUS symbol
renames and OnePlus additions. Replacing the main tree wholesale with the Reno
10x tree is therefore not an evidence-based fix for this CRC gate, though the
Oppo sources may still help with later device-specific gaps.

Required next evidence
----------------------
Obtain the exact /vendor/lib/modules binary set used in this successful-stock /
failed-v2 comparison, including modules.load, modules.dep, and modules.softdep.
The __versions tables can then be compared against this build's Module.symvers
to determine whether:

1. only module_layout differs and the actual layouts can be reconciled safely;
2. a small group of exported ABI CRCs differs and specific source/config drift
   can be identified; or
3. the vendor modules target a materially different unpublished kernel ABI.

Do not globally disable MODVERSIONS or blindly accept all mismatched CRCs. That
would permit code compiled for potentially different structure layouts to run
in kernel context and could corrupt memory before producing useful diagnostics.
